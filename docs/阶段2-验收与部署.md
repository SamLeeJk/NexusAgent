## 交付范围

本阶段提供 React/TypeScript 聊天页面、FastAPI 会话接口、PostgreSQL 业务数据、数据库持久化 LangGraph checkpoint、订单绑定提案、独立确认/拒绝、事务创建退款申请、故障后重试，以及明确标注的本地规则演示模式。

生产路径为 `main.py → api.py → service.py → workflow.py → database.py`。原有 `agent.py`、`tools.py` 与内存数据文件保留为第一阶段实验代码，不在 Web 服务中挂载。旧 `/chat` 返回 410，不能绕过新确认流程。政策检索继续复用 `retrieval.py`。

模型在新路径中负责结构化意图识别与跨轮订单指代；订单事实、申请资格、批准与执行结果由业务节点处理。此阶段没有让模型自动批准退款，也没有接入支付网关。

## 启动与访问

### 推荐：Docker 全栈演示

在项目根目录运行：

```bash
docker compose -p nexusagent-stage2 -f backend/docker-compose.yml up --build -d app
```

访问 `http://127.0.0.1:8000`。PostgreSQL 映射到本机 `55432`，容器内部使用 `5432`。应用和数据库端口均只绑定本机。

Compose 显式启用规则演示和种子数据，不会请求真实模型。演示账户：

- alice / demo-alice-123：O1001 已发货，O1002 处理中。
- bob / demo-bob-123：O2001 处理中。

种子数据只补缺失记录，不覆盖已经产生的申请。重复演示同一订单时，会返回已有申请编号，不创建新申请。

若 8000 已被占用，可在 PowerShell 先设置 `$env:NEXUS_HTTP_PORT='8001'` 再启动；浏览器改用对应端口。更换端口不更换数据库卷。

停止服务使用 `docker compose -p nexusagent-stage2 -f backend/docker-compose.yml down`，不要增加 `-v`，否则会删除演示数据卷。

### 本机开发

1. 使用 Python 3.12 的有效虚拟环境安装 `backend/requirements.txt`；其中包含测试依赖。容器使用精简的 `requirements-app.txt`。
2. 在 `frontend` 执行 `npm ci`、`npm run build`；构建文件由 FastAPI 同源提供。
3. 启动 Compose 中的 postgres 服务，按 `backend/.env.example` 配置本地 `.env`。
4. 在 `backend` 执行 `python migrate.py` 应用初始业务 schema 001 和 checkpoint 迁移，然后执行 `uvicorn main:app --host 127.0.0.1 --port 8000`。应用启动也会幂等执行迁移。

没有 PostgreSQL 时，可以在 `backend` 运行 `python run_local.py`。它显式选择本地 SQLite 文件和规则演示，文件保存在 `backend/runtime`；这不是 PostgreSQL 验证的替代，也不会静默修改默认部署配置。

本次开发环境原虚拟环境启动器不可用，验证使用已有 Python 3.12 运行时加载原环境依赖及项目 `.deps`。这些路径不是应用部署依赖，不提交依赖目录。

## 手动验收脚本

### A. 查询不产生申请

1. alice 登录，新建会话。
2. 输入“订单 O1002 能退款吗？”
3. 应显示处理中与退款资格；不出现已创建申请，也不自动写入退款记录。

### B. 多轮提案与刷新恢复

1. 在同一会话输入“帮我申请”。
2. 应出现标明 O1002、动作与有效期的确认卡。
3. 刷新页面，确认卡和历史仍在；用户继续点击确认。
4. 应显示申请编号，明确为“申请已提交”，不表示资金已退回。

### C. 服务重启

1. 在新会话中生成待确认提案，先不要确认。
2. 使用 `docker compose -p nexusagent-stage2 -f backend/docker-compose.yml restart app` 重启应用。
3. 刷新页面，登录态与待确认提案仍可查询；确认后得到申请结果。
4. 再次刷新，结果保留。重复确认同一提案仍返回同一结果。

### D. 取消与账户隔离

1. bob 登录，只能看到 O2001，不能看到 alice 的会话。
2. 针对 O2001 发起申请后点击取消，应显示取消结果，没有新的退款记录。
3. 输入“帮我申请 O1002”应得到统一的不可访问提示，不泄露该订单细节。

### E. 异常与恢复（自动化覆盖）

- 提案过期：确认得到 `expired` 终态，无写入，并解除会话等待。
- 提案生成后订单变为 shipped：得到 `invalidated`，无写入。
- 在确认接口中额外传入 order_id：422，拒绝篡改。
- 用另一个会话或用户提交该提案：404。
- 同会话同时操作：一个请求持有锁，竞争请求得到 409；之后可以重试。
- 同一 request_id 配不同文本：409；相同文本重试复用原请求。
- 数据库已批准但工作流未恢复、申请已写入但 checkpoint 未推进、消息记录已提交但响应丢失：重启后重试原决定，恢复既有结果，不增加申请。

## API 契约

写请求必须携带 `X-Nexus-Request: 1`。登录后使用 HttpOnly、SameSite=Strict 会话 Cookie；服务端只保存 token 哈希与有效期。没有开放跨域 CORS。演示账户不是完整生产身份系统，公网部署前需完善账户管理、速率限制和 HTTPS，并启用 Secure Cookie。

- `POST /api/login`：`{username,password}`。
- `POST /api/logout`、`GET /api/me`：会话管理。
- `GET /api/orders`、`GET /api/orders/{id}`：只读当前用户订单。
- `POST /api/conversations`、`GET /api/conversations`：创建和列出自己的会话。
- `GET /api/conversations/{cid}`：返回 messages、proposals、refunds、turns。
- `POST /api/conversations/{cid}/messages`：`{request_id: UUID,message}`；请求编号需要在重试时保留。
- `POST /api/conversations/{cid}/proposals/{pid}/decision`：只接收 `{decision: "approve" | "reject"}`。
- `GET /api/health`：数据库连通性、演示/模型模式和存储类型。

错误：401 未登录；403 缺少请求校验头；404 资源不存在或不可访问；409 并发/流程/幂等冲突；422 参数非法；502 模型服务错误；503 未配置模型；504 图执行步数超限。

提案过期、取消或资格改变是已处理的业务终态，确认接口返回 200 与状态/解释，不能仅按 HTTP 200 判断申请成功。只有 `completed` 加申请记录才代表登记成功。

## 状态与一致性设计

提案状态：pending → approved / rejected / expired；approved 经执行变为 completed / invalidated / expired。动作、用户、订单和有效期在服务端创建，客户端没有修改字段的入口。

LangGraph 流程：understand → resolve → approval（interrupt）→ execute。纯查询在 resolve 结束。持久化 thread_id 使用会话 ID，但每个 API 入口先校验会话归属。

审批接口先将决定写入数据库，再用 `Command(resume=...)` 恢复对应图。resume 值本身没有授权效力。执行节点读取数据库批准，再读取并锁定订单，复核身份、状态和有效期，最后在同一事务中写入退款记录与提案结果。

PostgreSQL 使用会话级 advisory lock 串行化同会话操作，事务内订单行锁和订单唯一约束保护写入。进程异常断开会释放 advisory lock。SQLite 演示使用文件锁，且业务状态与 checkpoint 分文件保存；跨进程共享路径是其运行前提。

跨业务事务和图 checkpoint 不声称分布式“恰好一次”。系统通过持久化请求 ID、确定性提案 ID、订单唯一约束、持久化结果和重试推进，实现本阶段定义的重复请求不重复创建申请。

## 验收边界

本阶段没有 SSE、向量检索、重排、完整管理员后台、真实付款、开放注册、密码重置或大规模压力测试。真实模型用例是小样本冒烟，不代表总体准确率。迁移 001 对应初始新数据库；未来 schema 修改应新增显式迁移，不依赖 create_all 修改旧列。
