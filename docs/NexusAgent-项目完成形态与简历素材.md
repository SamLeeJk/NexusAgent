## 一、本地实际进度：以源码为准

### 1. 已有实现

- **HTTP 服务**：`backend/main.py` 使用 FastAPI 提供 `POST /chat`，接收单条消息并调用 LangGraph；当前返回拼接后的调试消息，包含工具调用和工具结果，不是正式的聊天响应契约。
- **Agent 工作流**：`backend/agent.py` 实现 `confirmation → agent → tools → agent`，模型可选择四个业务工具；设置图递归上限 10。这是图执行步数限制，不等于完整的超时、费用或工具调用预算控制。
- **结构化意图判断**：使用结构化输出判断用户是否表达退款确认，结果写入 `AgentState.refund_confirmed`。
- **工具执行约束**：`backend/tools.py` 通过 `InjectedState` 注入确认状态，避免模型直接提供该工具参数；创建退款时再次检查订单存在、订单状态和重复请求。
- **订单与退款原型**：两个模拟订单，退款请求保存在进程内字典中；创建的是退款申请，没有支付退款能力。
- **初步词法检索**：政策文本按非空行切分，正则分词后通过 `BM25Okapi` 评分，返回分数最高的一条。这部分已经进入实际工具路径，README 中“BM25 尚未实现”的描述落后于工作区代码。
- **基础环境**：已有依赖文件、Qdrant Compose 配置。配置存在不代表服务正在运行，也不代表 Agent 已接入 Qdrant。

### 2. 尚未发现的实现

当前可见业务文件中没有 Web 前端、用户认证、订单归属检查、关系数据库、向量入库与查询、混合检索、重排、可靠来源引用、多请求会话记忆、持久化 checkpointer、人工审批中断与恢复、SSE 流式响应、评测执行器、自动化测试集或 CI 配置。

不要把 requirements 中的包当成已交付能力。当前适合定位为“客服 Agent 工具调用与 BM25 检索原型”，还不是完整全栈产品。

### 3. 下一步设计必须解决的问题

1. **确认没有绑定操作对象**：确认状态只有布尔值，没有绑定用户、订单、操作参数、有效期和审批记录。`InjectedState` 隐藏参数有价值，但上游确认分类器仍是模型，不能据此宣称授权完全可靠。
2. **资格检查信任模型参数**：`check_refund_policy(status, order_id)` 按传入状态判断，没有自行读取订单。因此可能出现资格回答与真实订单不一致；创建退款工具会重新读取订单，提供了一道执行保护，但不能消除错误解释。
3. **零相关内容也会返回结果**：BM25 直接取 `argmax`，即使查询完全无关，也会选出一条政策；缺少低相关回退。每次请求重建索引，按行分块也可能割裂未来的长文档。
4. **内存去重不是事务幂等**：重启丢失，多进程不共享，也没有数据库唯一约束，无法支撑跨进程并发一致性主张。
5. **多轮确认无法自然衔接**：每次 HTTP 请求初始化新状态，“可以，继续吧”无法可靠关联上一轮订单与待执行操作。
6. **调试信息直接作为产品响应**：应拆分用户可见答案、业务状态和受权限控制的服务端执行记录。
7. **启动行为仍需验证**：模型客户端在模块导入时构建，缺密钥环境下能否顺利启动并返回设计中的 503，不能仅凭路由内检查断言。

## 二、完成后这个项目是什么

### 项目名称与一句话定位

**NexusAgent——基于可控 Agent 工作流的智能售后客服平台。**

目标是构建一个连接聊天界面、政策知识库、订单系统和人工审批的全栈应用：用户用自然语言查询订单、理解售后政策、发起退款申请；系统提供可追溯答案，在身份、订单归属、业务规则和显式授权均满足时执行操作，遇到异常或证据不足时转交人工，并保留可检查的执行记录。

项目定位为可部署、可演示、可测量的个人作品。除非未来存在真实业务接入证据，否则不描述为企业正式上线系统，不声称真实客户规模或商业收益。

### 业务问题

传统 FAQ 能回答固定问题，但通常无法结合当前订单完成售后操作。仅让大模型调用接口，又容易出现政策引用不准确、把询问误判为执行指令、重复提交、会话中断后失去上下文，以及失败原因不可追踪等问题。

本项目要贯通“理解需求 → 查询事实 → 检索政策 → 形成操作提案 → 用户确认 → 业务校验 → 创建申请 → 查询结果”的闭环。业务价值目标是减少重复查找与录入、让售后处理过程更透明；实际节省时间与成功率需要后续评测或真实使用数据证明。

### 使用角色

- **客户**：登录、查看自己的订单、咨询政策、提交或取消待确认操作、查看申请状态。
- **客服人员**：查看待处理会话、审核升级工单、补充说明、接管异常请求。
- **管理员或维护者**：管理知识文档及版本，查看脱敏运行记录，运行评测并定位回归。

首版可以使用种子用户、模拟订单和模拟售后服务，但整个交互流程与权限校验应真实实现。

## 三、完成后的产品体验

### 1. 客户聊天工作台

前端采用 React 与 TypeScript 的建议方案，提供会话列表、历史消息、流式回复、检索来源、订单信息卡、退款确认卡和失败重试入口。展示“正在查询订单”“等待确认”等业务状态，不把内部提示词或完整调试转录暴露为聊天内容。

用户询问“我的订单什么时候发货”，系统在缺少订单编号时请求补充；有编号后查询当前用户有权访问的订单，再解释状态。用户切换会话、刷新页面或后端重启后，已持久化的历史与待审批任务仍可查询。

### 2. 可追溯的政策问答

用户询问“已发货还能退款吗”，系统检索当前生效的政策片段，返回结论及对应来源。点击来源可查看文档标题、版本和原文片段。

检索不到可信证据时，明确表示现有知识不能回答，并建议人工处理。具体订单的操作资格由结构化业务规则决定，不能让检索文本自行授予权限。政策文本和规则版本不一致时进入人工处理或阻止自动操作，避免一边答应、一边拒绝执行。

### 3. 退款申请闭环

用户表达退款意图后，系统先查询订单与资格，生成绑定订单的操作提案，在卡片中展示订单、申请类型和确认事项。用户点击确认后，服务端校验身份、提案有效期与参数是否一致，再恢复工作流。

执行阶段重新读取订单，检查归属、最新状态、重复请求与业务约束，在数据库事务内创建退款申请。回答“申请已创建”，展示申请编号和状态；没有支付网关接入时，绝不能说“款项已退回”。

### 4. 人工接管与审批

订单信息缺失、政策冲突、用户请求超出能力范围、连续工具失败时，创建人工处理任务。客服看到必要的订单信息、用户请求摘要、已采取动作和失败原因，能够作出审批或拒绝决定。

客户确认与客服审批是两种不同的授权：前者表示用户同意提交申请；后者处理需要人工判断的业务例外。两者均需独立记录与权限检查。

### 5. 知识和运行管理

维护者上传或更新政策文档后，系统完成解析、分块、索引与发布，展示文档版本和索引状态。执行详情页展示检索命中、工具调用、审批、耗时和错误分类，支持按会话或请求定位问题。

## 四、目标技术架构与工程设计

### 1. 分层与建议技术栈

- **展示层**：React、TypeScript；负责聊天、审批、订单与知识管理交互。具体构建工具和 UI 库可在实现时选择。
- **API 层**：沿用 FastAPI，统一身份校验、输入验证、业务响应、SSE 事件及错误处理。
- **运行控制层**：基于现有 LangGraph 增加 runtime harness，负责状态、工具执行门禁、审批、预算、恢复和运行记录。
- **领域服务层**：订单服务、退款申请服务、知识检索服务；关键业务规则保留在确定性代码与数据库约束中。
- **存储层**：建议 PostgreSQL 存业务数据及持久化会话状态；Qdrant 存向量与文档元数据；BM25 索引负责词法检索。
- **验证层**：pytest 业务测试、前端端到端测试与 Agent evaluation harness；以版本化用例和报告支持迭代。
- **部署层**：补充应用容器、数据库、Qdrant 的 Compose 环境、迁移与种子数据、健康检查和配置说明。

首版保持单 Agent 加明确业务节点即可。只有实际场景证明需要不同专业角色协作时再引入多 Agent。Redis、消息队列、Kubernetes 也不作为默认完成条件。

### 2. 建议的数据模型

- `users`：身份和角色；订单按用户绑定，服务端验证访问范围。
- `orders`：订单编号、用户、当前状态、业务版本、必要的展示字段。
- `refund_requests`：申请编号、订单、申请人、状态、幂等键与创建时间；首版“同一订单只允许一个申请”的规则可用唯一约束表达。未来支持撤销再申请时应重新设计约束。
- `conversations/messages`：会话所有者、消息角色、内容、时间和用户可见状态。
- `action_proposals/approvals`：待执行动作、订单、参数摘要、申请用户、有效期、审批主体、决定和消费状态。
- `documents/chunks`：政策来源、版本、生效状态、分块编号与索引状态。
- `agent_runs/run_events`：请求关联、阶段、工具状态、耗时、错误和可用的模型用量。

LangGraph checkpoint 与业务记录职责不同：checkpoint 用于恢复图执行，退款表用于确定业务结果。图恢复不能替代事务幂等；日志也不能替代业务事实。

### 3. 接口与流式交互

建议接口包括：创建和查询会话、提交消息、订阅运行事件、确认或拒绝操作提案、查看退款申请、管理知识文档、查询授权范围内的运行详情。

提交消息时传入会话标识和客户端请求标识；服务端验证归属并创建运行记录。同一会话并发发送应排队或明确拒绝，防止两次运行覆盖上下文。SSE 事件可定义为文本增量、阶段更新、来源、待确认操作、完成和错误，每个事件带运行 ID 与序号。

断线后先查询运行状态或从已保存事件继续展示，不能因为重新连接就再次执行退款。SSE 只负责传输，不天然提供重放与业务去重能力。

### 4. RAG 设计

文档接入按“解析 → 保留标题结构的分块 → 来源与版本标记 → 建立索引 → 发布”组织。短政策不必强行做复杂切块，长文档则需保留规则前提与例外关系。

检索从现有 BM25 基线演进为 BM25 与向量检索并行召回，按稳定的分块 ID 去重，使用 RRF 等排序融合方式，避免直接相加量纲不同的原始分数。可选重排器应通过评测证明增益后再保留。

回答只引用实际召回且适用的片段，包含可解析的来源 ID。设置证据不足回退，并通过标注集调整判定策略，不假设存在适用于所有查询的万能分数阈值。若支持中文政策，应单独验证当前正则分词是否足够，选择合适分词与嵌入方案。

语义相似度不能决定是否批准退款。执行前应按权威订单与业务规则重新校验；文档内容只作为参考数据，不能被当成系统指令执行。

## 五、是否引入 harness：建议引入，但职责要具体

这里将 harness 理解为围绕 Agent 的运行控制与评测设施，不特指名为 Harness 的商业交付平台。

**结论：适合引入轻量 runtime harness 和 evaluation harness，继续复用 LangGraph。** 当前已经存在图循环、状态注入、业务守卫与步数限制，可作为起点；还不能据此称为完整 harness。

### 1. Runtime harness：控制一次客服任务如何执行

这是本项目自行设计的应用运行层，而非要求替换现有模型或重写工作流框架。

- **上下文管理**：按用户与会话加载历史，保存当前订单、待执行提案和关键事实；长会话可摘要，但审批凭据与权威业务状态不能仅保留为模型摘要。
- **工具注册与门禁**：区分只读查询与写操作，为写操作校验身份、资源归属、批准的参数和幂等键。模型提议动作，执行层决定是否接受。
- **显式审批**：形成操作提案并暂停执行；经过认证的确认接口消费对应批准记录，再恢复指定运行。不能让模型自行填写“已审批”。
- **资源约束**：设置任务截止时间、模型调用次数、工具次数与可配置用量预算；触达限制时保存状态并给出可理解结果。
- **错误与重试**：对可重试的只读请求限制次数并退避；写操作遇到超时先按幂等键查结果，避免盲目重试制造重复动作。
- **恢复与终止**：利用持久化 checkpoint 恢复等待中的任务；用明确业务状态标记成功、失败、取消或转人工，不能只依赖模型说“完成了”。
- **可观测性**：记录可见消息、检索结果、工具入参与返回、审批事件和耗时；脱敏处理，不采集或声称展示模型隐藏思维链。

建议运行流程为：身份校验 → 加载会话 → 查询或检索 → 生成操作提案 → 暂停等待确认 → 校验批准 → 事务执行 → 保存结果 → 返回答案。纯查询走较短分支。

LangGraph 官方文档说明，interrupt 配合 checkpointer 与 thread ID 支持暂停和恢复；恢复时节点会重新执行，因此副作用必须谨慎放置并保证幂等。本项目据此设计“审批节点”和“执行节点”的边界。[官方说明](https://docs.langchain.com/oss/python/langgraph/interrupts)

### 2. Evaluation harness：证明修改是否改善系统

构建可重复执行的用例集、隔离数据、运行器、评分规则和报告。区分答案质量与最终业务状态：回答“申请成功”不等于数据库中真的只创建了一条正确申请。

用例至少包含输入消息序列、初始订单状态、用户身份、期望业务结果、禁止动作、预期引用来源与可选工具约束。避免把所有工具调用顺序写死，允许合理的等价路径；授权与写操作前置条件则必须强制检查。

采用两层运行方式：离线使用可控模型替身验证状态机、权限和幂等；在线在隔离数据上使用真实模型验证意图理解、检索和回答。前者不能替代后者。每次运行记录提交、提示词、模型标识、索引版本、参数和用例版本。

业务不变量通过代码断言验证，回答的引用支持度可结合人工标注与经过校准的模型评分。失败样例保留轨迹用于复现，评测不得触达真实付款工具。

此设计参考 Agent 评测中任务、运行轨迹、评分与最终环境状态分离的思路；具体用例和判据是本项目建议。[参考资料](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### 3. Development harness：辅助我们把项目做完

如果你所指的是让 AI 跨多次会话持续开发的 harness，还可以增加功能验收清单、当前进度文件、统一启动命令与验证入口。每次开发读取现状，只交付有限范围的功能，验证后更新证据，未验证功能不能标完成。

这属于开发过程设施，与客服系统运行时是两件事。可作为工程实践补充，但项目简历的主体应仍是用户可使用的业务闭环。该思路可参考长期运行编码 Agent 的环境初始化、增量交付与交接记录模式。[参考资料](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

## 六、完成后的关键难点与可展开的技术内容

### 难点一：自然语言意图不能直接变成业务授权

“能退吗”和“帮我提交”必须区分，但分类准确并不等于有权操作。最终方案将意图理解、操作提案、显式确认与确定性校验拆开，并把确认绑定到具体用户、订单与参数。

可追问：为什么原有布尔确认不够？如何防止确认 A 订单却执行 B 订单？审批过期或订单状态变化怎么办？

### 难点二：多轮记忆与写操作一致性

系统需要记住用户在说哪张订单，又必须在重启、重复请求和网络超时后保持正确业务状态。方案组合持久化会话、checkpointer、数据库事务、唯一约束与幂等结果查询，并处理同会话并发。

可追问：数据库已提交但响应丢失如何处理？checkpoint 恢复为什么可能重复执行？为什么内存字典去重不够？

### 难点三：检索命中不代表答案可信

需要区分词法匹配、语义相近和规则真正适用。方案保留 BM25 基线，按证据比较混合检索，约束来源版本与回答引用，并覆盖无答案和政策冲突案例。

可追问：当前 Top-1 为何会误答？为什么选排序融合？如何证明重排值得增加的延迟？

### 难点四：前端状态与后端实际运行保持一致

聊天不仅有文本，还存在执行中、等待确认、失败和已完成等状态。前端根据有类型的事件与服务端状态渲染，刷新或断线后重新读取结果，提交确认时做防重复交互，服务端仍独立幂等。

可追问：浏览器断线时任务是否继续？如何避免重复显示？用户连点两次确认为什么不会创建两笔申请？

### 难点五：可重复地衡量 Agent 的变化

模型具有随机性，单次演示成功不足以证明可靠。用固定测试集、多次试验、轨迹和业务状态断言区分检索失败、推理错误、执行失败与基础设施错误，再对比不同版本。

## 七、评测与验收：预先定义口径，不预填成果

以下是建议验收项，尚无实测结果。

### 核心场景

1. 查询本人订单，返回对应状态；查询不存在或他人订单，不泄露受限信息。
2. 仅询问退款资格，不创建申请。
3. 符合条件的订单，经对应用户确认后，仅创建一条申请。
4. 已发货或状态发生变化的订单，按当前业务规则拒绝自动申请。
5. 修改订单参数、使用过期批准、重放批准，均不能绕过执行约束。
6. 双击、并发提交或写后响应超时，不产生重复申请。
7. 后端在等待确认时重启，任务可恢复，批准仍绑定正确操作。
8. 无关知识问题不强行给出退款政策答案；引用能够回溯到生效文档。
9. 文档包含诱导指令时，不改变工具权限与执行规则。
10. 检索、模型或工具失败时有清晰失败状态，必要时转人工。
11. 前端流式断线和页面刷新后，可恢复已保存的会话与运行结果。
12. 修改模型或提示词后，安全用例与业务回归没有新增失败。

### 指标定义

- **任务成功率**：同时满足该用例答案要求与最终业务状态要求的运行数 / 有效运行总数，按场景分别报告。
- **未授权执行数**：不满足身份、归属、批准或业务规则时仍产生写入的次数；作为测试集上的硬性门禁，目标为零，不据此宣称现实中绝对安全。
- **重复写入数**：重复请求与并发实验中超出允许数量的业务记录数。
- **Recall@k**：有标注相关片段的查询中，召回的相关片段占全部相关片段的比例；若每题只标一个目标片段，可另外报告 Hit@k。
- **引用支持率**：抽样答案中需引用的事实性主张，被所引原文支持的比例，明确评分方法与样本数。
- **延迟**：分别记录首个用户可见输出时间、纯查询完成时间及不含人工等待的机器处理时间，报告样本数与 P50/P95。
- **模型用量与成本**：记录供应商返回的实际用量；若换算费用，注明计价日期和模型价格，无法取得的数据不估装成实测。
- **恢复成功率**：在规定故障注入位置中恢复并达到正确业务终态的次数 / 尝试次数。

比较 BM25、混合检索和可选重排时，保持文档、查询集及生成配置一致；调参集与最终验证集分开，报告退步场景。正式简历中的数字只能来自保存下来的实验报告。

## 八、建议交付顺序与完成标准

### 阶段 1：收敛当前原型

修复文档落后问题、检索无答案回退和资格查询的数据来源；拆分最终答案与调试记录，验证无密钥启动、工具拒绝分支和基本检索。完成标准：当前功能可重复运行，有明确输入输出和离线验证证据。

### 阶段 2：打通全栈业务闭环

加入前端、身份与订单归属、PostgreSQL、会话持久化、操作提案和确认界面、事务退款申请。完成标准：浏览器里能从咨询走到确认提交，再查询申请；刷新、重复点击和越权访问行为正确。

### 阶段 3：落地运行 harness

增加持久化中断恢复、预算与超时、幂等重试策略、人工接管和执行事件。完成标准：等待确认时重启、写后响应丢失及工具超时均有可演示的处理结果。

### 阶段 4：补齐知识检索与评测

接入文档版本、向量检索、混合召回与来源展示，并用评测判断是否需要重排。评测用例应从阶段 1 起积累，此阶段形成批量执行与对比报告。完成标准：检索变化有可复现证据，业务不变量有自动回归保护。

### 阶段 5：形成可交付作品

补齐部署说明、数据库迁移、种子数据、健康检查、CI、演示脚本与脱敏截图。完成标准：新环境可以按文档启动，从浏览器完成正常与异常场景，关键主张能定位到代码、用例和运行报告。

## 九、可交给 AI 理解的“完成后项目介绍”

**本节为目标态叙述，只有对应功能完成并验证后才能改成已完成经历。**

NexusAgent 计划建设为一个面向电商售后场景的全栈智能客服平台，将自然语言交互、订单查询、政策检索、退款申请与人工接管整合为完整业务流程。客户可以通过 Web 聊天工作台查询订单、查看带来源的政策解释，并在明确确认后提交退款申请；客服人员可以处理升级任务，维护者可以管理知识版本并追踪系统执行情况。

系统计划采用 React 与 TypeScript 构建前端，FastAPI 提供业务和流式接口，LangGraph 编排客服任务，PostgreSQL 管理业务记录与持久化状态，BM25 与 Qdrant 支持混合知识检索。业务服务负责校验用户身份、订单归属、退款资格和幂等条件，模型负责理解需求、选择查询工具和组织解释。

核心工程设计是在现有 Agent 外围建设轻量运行 harness：管理跨请求上下文、绑定操作对象的确认记录、暂停恢复、工具权限、执行预算和运行事件。对于有副作用的退款申请，通过显式确认、执行前重新校验与数据库事务保证流程可控；对于失败与不确定场景，保留状态并转交人工。

项目还计划建设 evaluation harness，以版本化多轮用例、隔离订单数据、业务状态断言与运行轨迹，对任务成功、越权行为、重复提交、检索质量、延迟和用量进行回归评估。最终交付包含可部署应用、可演示业务闭环、异常恢复场景与可重复评测报告，体现前后端交互、数据一致性、AI 工作流和工程验证能力。
